Basket: a data collection platform, built two times

Lead engineer and technical owner · 2024–2026

Context

Basket is a shopping app. Users save products from any online shop. The platform must get the price and the availability for each saved product URL, from more than 30,000 shops, without special code for each shop.

I joined in March 2024. The platform was live and other engineers had built it before me. I improved it for two years, then designed and built a new version and did the production cutover in March 2026. My scope grew to AWS, GCP, Firebase, MongoDB Atlas, BigQuery, the proxy infrastructure, data collection, product ingestion and a Kubernetes cluster with the vector database. I was the technical lead of a team with 2 mobile developers, 2 full-stack developers and 1 designer.

The problem

  • Most product pages are JavaScript apps. The first HTML is empty. A headless browser costs 10 to 50 times more than a plain request.
  • Anti-bot systems check the TLS fingerprint, the HTTP/2 settings and the header order of the client before they send any HTML.
  • Residential and mobile proxies help with IP reputation, but the price is per request. If every block goes to a paid proxy, the cost grows with the volume.
  • A page that loads may not contain the product. Some shops return status 200 for a bot challenge, return 404 for out-of-stock pages that still contain the product data, and redirect expired products to the home page.

Platform 1 (2024–2025): Kubernetes on EKS and GKE

  • Two EKS clusters: one for development and staging, one for production. Terraform Cloud with one workspace for each environment.
  • One ArgoCD installation manages all clusters. Each environment is an app of apps, with a Kustomize base and an overlay for each environment.
  • Karpenter provisions the nodes. General work, GPU work and batch jobs have separate node pools. The vector database runs on on-demand nodes that do not expire.
  • A browser farm of Puppeteer Chromes, with a queue limit that can change at runtime and horizontal autoscaling.
  • Alerts as code: CloudWatch alarms go through SNS and Lambda to Slack. They cover the Lambda success rate, Step Functions failures, queue age and the extraction success rate. Prometheus and Grafana show the rest.
  • The visual search ran on a separate GKE cluster: Weaviate with 3 replicas, each on its own node, and GPU node pools for the CLIP and re-ranker models.
  • Weaviate backups go to Cloud Storage. A separate cluster restores them, to prove that the restore works.

Platform 2 (2026): the rewrite on GCP

After two years the architecture was the limit. Cost and performance work could not go further.

  • The core library contains only business logic. It has no cloud dependencies. The infrastructure comes in through four interfaces: database, queue, storage and event sink. So the tests run without credentials.
  • A short orchestrator function replaced the old chain of functions and a Step Function with 35 states.
  • Cloud Run services for the API, the processor, the workers, the admin dashboard and a self-hosted render service. Pub/Sub between them, with retries.
  • One PostgreSQL row for each URL is the single source of truth. The mobile app reads it directly.
  • Each attempt writes a typed event to BigQuery. An execution ID connects all events of one request.
  • Before the cutover, the old and the new versions ran side by side on the same product batches. The new version had a better cost, time and success rate. Then I switched production and checked the dashboards, the live app and the tests.

I built the new version in approximately two weeks. AI agents wrote the code to my design and under my review. The setup for this took one year: repository instructions, a shared skill library, read-only data access for the agents and a model choice for each task.

The fetch sequence

All sources use one contract and one definition of success. The cheapest and most precise sources go first: data that the app already has, cached HTML, affiliate feeds and shop APIs. After that, a generic fetch goes through 5 cost levels:

  1. A direct request.
  2. An HTTP client that sends the same TLS 1.3 handshake, HTTP/2 settings and header order as a current Chrome.
  3. Our own 4G mobile lines. After a block, the line gets a new IP address. The carrier allows this once in 6 minutes.
  4. Self-hosted Chrome, first from a datacenter IP address, then through a dedicated 4G line.
  5. Paid vendors, only for the hardest pages.

No provider decides that it was successful. Every response goes to the same extractor. Four parsers run in parallel (LD+JSON, shop XPath, microdata and OpenGraph), and the result for each field comes from the parser with the highest confidence. Success means title, price and currency, or title and out of stock. A bot challenge goes to the next level. An out-of-stock 404 is a success. An expired redirect stops before the paid levels.

  • ~95%less traffic to paid proxy providers
  • ~97%of pages need only our own infrastructure
  • $3,000 → $975ScrapingBee cost per month

Failure diagnostics

For a long time we thought that most failed pages were blocks. When every attempt was measured by the extracted data, the result was different: blocking caused less than 5% of failed pages. Most failures were extraction errors. So the next work went to extraction.

  • Trigger: the extractor gets the page, but not enough data. For example, there is no price.
  • Signature: HTTP status group, body size group, extraction method, extraction status and redirect state, hashed with the shop domain.
  • One LLM request for each shop and signature in 7 days. Thousands of pages that fail in the same way cost one request.
  • The model is Gemini Flash-Lite on Vertex AI, with a fixed JSON schema and temperature 0.1. It returns the page type, the product state, the block vendor, the cause of the failure and the location of each field (DOM selector, LD+JSON or Next.js data).
  • When the confidence is 0.75 or more, the system marks expired pages automatically and records known block vendors in the shop profile.
  • The results go into a knowledge base for each shop. The team sees it in the admin dashboard.

The LLM explains failures. The production extraction uses the four parsers.

Other systems on the same platform

  • SHEIN data source. It updates 4.4 million products every day for approximately $350 per month. To buy the same data from a data vendor would cost approximately $15,840 per month.
  • Visual product search. With a small team, I built core parts of a search over 25 million products: Grounding DINO and SAM2 find the product in the image, CLIP makes the embedding, Weaviate stores it and a re-ranker sorts the results. Ingestion ran at approximately 800 products per minute. I wrote the orchestration service for this pipeline in Go.
  • Shopping assistant. One router and four specialist agents with strict JSON contracts. Retrieval from several sources with semantic re-ranking. I wrote the evaluation together with the agents: golden question sets, routing accuracy and LLM-as-judge scores for each version. We chose the model for each task with A/B tests across OpenAI and Gemini.
  • Product-feed service. A batch job builds a new LMDB store from affiliate feeds and swaps it in while the API continues to serve. Load test: 1,000 virtual users, approximately 900 requests per second, p50 53 ms, p95 157 ms, no failures.
